# AGENTS.md

Тестовое задание T-LAB, направление **World, Action & Reward Models**.
Постановка целиком — в [NOTES.md](NOTES.md). Прочитай её перед любой работой.

## Раскладка

| путь | что там | в git |
|---|---|---|
| `NOTES.md` | задание, сетап, грабли, предсказания, лог, результаты | да |
| `baseline.py` | наивный файнтюн на 5/10/25 демо + eval, обёртка над LeRobot CLI | да |

## Правила

- **Бейзлайн замораживается.** Числа из `baseline.py` на 5/10/25 — точка отсчёта для
  Задачи 2, менять их задним числом нельзя.
- **Демо берём первые по порядку** (`demo_subset.py`), не выбираем удачные.
- Демо других целевых задач использовать **нельзя**; демо seen-задач — можно;
  собирать новые данные в среде — нельзя, среда только для оценки.
- Каждая точка кривой: 3 целевые задачи $\times \ge 20$ эпизодов $\times \ge 2$ сида.
- **Предсказания пишутся в NOTES ДО запусков.** Это оценивается отдельно, и задним
  числом не восстанавливается.
- Все запуски пишут строку в `runs/results.jsonl` (это делает `baseline.py eval`).
- **Граница кода.** Корень — код человека: `baseline.py`, `demo_subset.py`,
  `cost_curve.py`, финальный метод. `tmp/` — территория агента: варианты адаптации,
  одноразовые скрипты, логи, разборы. Там можно что угодно, но по-человечески читаемо.
- Из `tmp/` в корень переезжает только то, что доказало пользу, — причёсанным и со
  строкой в NOTES → «Лог».
- **На macOS работает всё, включая симулятор** (`./setup_macos_libero.sh`, `MUJOCO_GL=cgl`).
  Ограничение не в совместимости, а в скорости: 20 шагов/с, то есть эпизод ~15 с без
  политики. Локально — диагностика, zero-shot, разбор фейлов на единицах эпизодов.
  Полная кривая (480 эпизодов + обучение) — на удалённой GPU.

## Граница ответственности и доказательства

- Код реализует только согласованный текст из `OWNER_NOTES.md`, `NOTES.md` или
  указанной статьи. Перед новой реализацией запиши источник и точное соответствие
  «метод адаптации → параметры политики → данные → eval». Если текст не определяет
  решение, спроси владельца.
- Для каждого датасета фиксируются Hugging Face repo, revision, suite, task IDs и
  episode IDs. `libero_object` не заменяет `libero_90`. Seen-претрен не считается
  выполненным, пока не проверена именно согласованная конверсия `libero_90`.
- Метод из статьи получает её имя только после сверки первоисточника и авторского
  кода. LoRA, mix, augmentation, chunking и bonus A считаются отдельными идеями с
  собственным происхождением. Bonus A сейчас нельзя помечать реализованным без кода,
  action-free данных, диагностики и запуска.
- Не добавляй новые CLI-флаги и оболочки над флагами LeRobot. Фиксированные
  эксперименты запускаются обычными Python файлами; общие model, training, eval и
  recorder переиспользуются.
- Дамп конфига не доказывает, что настройка применена. В лог пишутся фактические
  learning rate по шагам, scheduler, trainable parameter groups, число показов
  целевых и seen-демо, dataset revision, завершение обучения и путь нового чекпойнта.
  Eval не запускается после ненулевого кода возврата или без чекпойнта этого запуска.
- Диагностика сохраняет реальные кадры, инструкции, действия, action chunks,
  предсказания, ошибки по времени, внутренние состояния выбранных модулей, градиенты
  и роллауты. Новая метрика или правило отбора требует согласования.
- `NOTES.md` содержит одну таблицу идей
  `ID | источник | точный метод | статус | код | диагностика` и одну таблицу запусков
  `run | протокол | статус | лог | артефакты | вывод`. Непроверенный или неверно
  реализованный запуск не считается отрицательным результатом метода.
- Черновой код и ошибочные попытки остаются восстановимо в `tmp/`. В корень попадает
  только согласованная финальная вариация. Следующий шаг в цепочке аргументов не
  выполнять без подтверждения владельца.
- Каждый запуск должен быть виден в Training Observer. Локальный запуск использует
  Anyflow, запуск на A100 использует ClearML; точный адаптер и набор полей сначала
  согласуются. Выбор MPS/CUDA, workers, dtype, batch size, optimizer, stopping rule и
  seed выводится в лог как фактически применённая конфигурация.

## История и передача состояния

Следующая сессия начинается с чистого листа и видит только репозиторий. Всё, что не
записано, потеряно.

- **Каждое законченное изменение — отдельный коммит, сразу.** Не копи правки пачкой.
- Сообщение коммита — по-русски, в повелительном наклонении, про **почему**, а не
  только что: «Починить выбор демо под формат v3.0» вместо «фикс». Если решение
  неочевидное — второй абзац с обоснованием и тем, что отвергли.
- **Состояние проекта живёт в `NOTES.md`.** После каждого прогона — строка в «Лог»:
  дата, команда, число, вывод. После каждого решения — почему так, а не иначе.
  Отрицательный результат записывается наравне с положительным.
- Нерешённое — в «Открытые вопросы», чтобы следующий не переоткрывал их заново.
- **Начало сессии:** `git log --oneline -15` плюс «Лог» и «Открытые вопросы» в NOTES.
  Этого должно хватить, чтобы понять, где всё стоит, без чтения переписок.

## Поправки заказчика: читать перед каждой задачей

Собрано из того, что приходилось поправлять по ходу. Порядок — по частоте, с какой я
на это натыкался.

**Бейзлайн — ровно по статье.** Не по конспекту, не по пересказу, не по памяти. Открыть
первоисточник (на arXiv есть HTML-версия), прочитать целиком, выписать алгоритм и
гиперпараметры, и только потом писать код. Поправка на нашу задачу и размер модели
допустима и должна быть записана явно; отступление от метода — нет. Уже стоило одной
полной переделки: `p(1-p)` был взят из конспекта, а SFL оказался отдельным циклом поиска,
а не другой score-функцией внутри PLR.

**Проверять на маленьком, потом запускать большое.** Сначала прогон на десятках шагов,
который отвечает «код работает и лосс падает». Потом короткий отсев — час на скрипт.
Полные прогоны идут на A100, не здесь. Промежуточные запуски намеренно неполные: один
сид, урезанный бюджет, одна задача — это не нарушение условия, это отсев.

**Сиды и повторы на этом этапе не нужны.** Важно, шевелится идея или нет, а не третий
знак после запятой.

**Диагностика — не приложение к эксперименту, а сам результат.** Логировать по ходу
обучения, а не только в конце: градиент по блокам, ранг, спектральный радиус, полезность
шага, распределение softmax. В конце — полный разбор.

**Отрицательный результат с честным разбором ценен.** Не подгонять эксперимент под
ожидаемый ответ и не менять метрику, когда результат не нравится. Если идея не
сработала, надо понять механизм и записать.

**Коммит на каждое законченное изменение, сразу.** Сообщение по-русски, про «почему», а
не только «что». Неочевидное решение — вторым абзацем с обоснованием и тем, что
отвергли.

**Состояние живёт в NOTES.md.** Следующая сессия видит только репозиторий. Что не
записано — потеряно.

**Логи экспериментов в JSON, визуализация из них.** Не статичные картинки: `viz.py`
собирает самодостаточную страницу из того, что записали прогоны.

**Код в стиле кодовой базы, минимум строк, переиспользовать модули.** Своё черновое — в
`tmp/`. В корень переезжает только доказавшее пользу, причёсанным. Одна ошибка должна
чиниться в одном месте.

**Фоновые задачи — только отслеживаемым механизмом.** Запущенное через `nohup &` не
присылает уведомления, и очередь встаёт незаметно.

**Не ждать длинный прогон — переходить к следующему методу.** Прогон, который идёт
часами, не должен блокировать очередь: пока он считает, надо реализовывать и отсеивать
следующую идею. Проверять состояние очереди явно (что живо, на каком шаге, когда
последняя запись в логе), а не считать, что «наверное, ещё идёт». Скрипт отсева
пропускает уже посчитанное, поэтому его можно перезапускать сколько угодно.

**Пропуск посчитанного проверять по результату, а не по наличию файла.** Оборванный
прогон оставляет частичный `history.json`, и следующий запуск молча его засчитывает.
Проверять надо строку с финальной метрикой.

**Не освобождать машину «на всякий случай».** Прежде чем что-то убивать — посмотреть, что
там считается и не жалко ли.

**Архитектуру показывать до реализации.** Схема и размерности на согласование, потом код.
